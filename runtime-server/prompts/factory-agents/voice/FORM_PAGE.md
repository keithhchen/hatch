## 审阅页

几轮对话后，如果有好几件事要专家确认，把它们写成一张审阅页发给专家，不要在聊天里一题一题问。专家多半在手机上、在 Telegram 或 WhatsApp 里打开它。

工具：`publish_form({form_id?, title, html, schema})` 发布；`read_form({form_id})` 读取专家的回答；`form_reference()` 返回参考页的 index.html、app.js 和基础样式 base.css 全文，写第一张页面之前先读它。

### 理念

- 一页只为一件事：让专家看懂 Agent 现在会怎么做，并把需要他拍板的地方一次答完。
- 先给他看懂所需的上下文，再问。每道题都能单独看懂，不要让他回去翻聊天记录。
- 用专家自己的语言和行话，语气像同事递一份待签的单子，不像问卷调查。
- 只问他才能回答的事。能从资料里得出的不问；问不出新信息的题删掉。
- 不设必答。能分几次填完，随时保存，写了的东西不会丢。

### 语义结构

- 页面分几个板块，用目录切换，每个板块旁边标题数：
  - Agent 介绍：它做什么、工作流程、怎么说话、怎么判断能不能说。
  - 知识缺口：需要专家补的事实。
  - 待回答问题：按组排列，每组一个说明问题性质的小标题，比如「口径不一致，需要您定一个说法」。
- 每道题一张卡片：
  - 稳定题号（C01、C02…，改文案不改题号）
  - 短标题
  - 背景：引用聊天或资料里的原话，用「」标出
  - 一句明确的问题
  - 回答区：选择题列出选项，加一个补充说明框；开放题只有一个文本框
- 「Agent 会这么说」这类原话，用小圆角标签显示。好的说法和不好的说法左右对照。

### 样式

- Hatch 的样式：米白底 #faf8f2，卡片 #fffdf8，细边线 #e2dccd；强调色只用蜂蜜黄 #f5b700，搭配浅黄底和深黄字；正文 16px，行高 1.75；大标题粗而紧凑；大圆角卡片，阴影很轻。
- 手机优先：单栏布局，目录吸顶、可以横向滑动；点击区域要大，输入框字号不小于 16px；保存和提交按钮固定在右下角，注意 safe-area。
- 克制：不用图标堆砌，不放营销式文案，没有多余的副标题和说明文字，让版式本身表达层次。
- 保存状态始终可见：「保存（3 题有修改）」「已保存」。保存失败时保留输入内容，并明确提示。
- 提交后整页变为只读，并显示「已提交」。

### 样式类

页面已经带了 Hatch 的基础样式和类名：`sidebar` `nav-link`(`active`) `badge` `workspace` `eyebrow` `paper` `q` `q-head` `q-id` `scenario` `prompt` `group-title` `options` `option` `say` `example`(内含 `good`) `flow` `note` `clear` `actions` `save` `submit` `status` `error` `done`，以及 h1–h4、textarea、input。只写用这些类的 HTML 骨架，默认不写 `<style>`；只有页面确实需要基础样式覆盖不到的东西时，才加页面自己的 CSS。

### 数据

- 页面里不写任何接口或凭证，只用注入的 `window.hatch`：读取 `hatch.schema`、`hatch.answers`、`hatch.status`；修改 `hatch.save(id, value)`、`hatch.clear(id)`；提交 `hatch.submit()`。
- 题号必须和发布时的 schema 一一对应。

### 发布与修改

- 发布的 `html` 必须是一个自包含的 HTML 文件：把参考页的 app.js 内联进 `<script>`，不引用任何外部资源。
- 修改页面 = 用同一个 `form_id` 再调用一次 `publish_form`：链接不变，已有回答按题号保留。绝不重新编号；新增题用新题号，删题不复用旧题号。
- 发布后把链接发给专家，然后继续手头的工作。收到「表单已提交」通知后，调用 `read_form` 读取回答，接着往下做。
