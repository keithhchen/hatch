## 审阅页

几轮对话后，如果有好几件事要专家确认，把它们写成一张审阅页发给专家，不要在聊天里一题一题问。专家多半在手机上、在 Telegram 或 WhatsApp 里打开它。

工具：`publish_form({form_id?, title, html, schema})` 发布；`read_form({form_id})` 读取专家的回答；写第一张页面之前，先用 `read` 读参考页 `input/reference/review-page.html`，照它的结构和类名写。

### 理念

- 一页只为一件事：让专家看懂 Agent 现在会怎么做，并把需要他拍板的地方一次答完。
- 先给他看懂所需的上下文，再问。每道题都能单独看懂，不要让他回去翻聊天记录。
- 用专家自己的语言和行话，语气像同事递一份待签的单子，不像问卷调查。
- 只问他才能回答的事。能从资料里得出的不问；问不出新信息的题删掉。
- 不设必答。能分几次填完，随时保存，写了的东西不会丢。

### 写什么

- 先读资料和 `output/CREATOR_PERSONA.md`，问题立在里面的事实和原话上；资料已经答了的不问。
- 每道题 = 背景（资料或对话里的原话、事实）+ 一句提问，不放光秃秃的问题。
- 每个技能一个板块：什么时候走它（客户问什么、什么情况）、他的规则、例外、什么时候交给真人。
- 知识缺口必须有：「下判断前你必须先问客户什么」「遇到没做过的情况你怎么说」。
- 资料或聊天里说法冲突（价格、起订量、政策），做成一道选择题「说法不一致，请定一个」，把各种说法列成选项，再加补充框。这是整页最有价值的题。
- 要声音样本：直接在页面上问「你对客户说过一百遍的话」、怎么称呼客户、怎么拒绝。
- 说话的人不是专家本人（助理、员工）时，告诉他页面会转给专家，并把页面写成专家一个人、用文字就能答完。
- 语气平实，不戏剧化。

### 页面骨架（示例）

真实的审阅页是这个形状：先让专家看懂 Agent 现在怎么做（介绍），再按组问，一张页 15–25 题，少于 10 题说明有层没覆盖。下面是婚礼摄影师的骨架，只示范结构，别照抄措辞：

- Agent 介绍（不是题）：工作流程；怎么说话；怎么判断能不能说（标准口径 / 待确认 / 没有记录）；每个技能一块：什么时候走它（触发）、它知道的、它怎么做、什么时候交给真人。技能块是 Agent 目前的理解，由专家来改。
- 分组问题，每组一个说明性质的小标题：
  - 「说法不一致，需要您定一个」（约 10 题）：背景引用原话列出各种说法，「聊天里出现过三种说法：『定金三成』『定金五百』『先付一半』」，问「对客户统一说哪一个？」，选项就是这三个说法，加补充框。说不成选项的，写成开放题：「有外地场次时，是一律加差旅费，还是有例外？」
  - 「知识缺口」（约 7 题）：背景写资料里缺什么、Agent 现在只能怎么答，「聊天里没有出现过改期规则，客户常问，Agent 现在只能说『我请同事确认』」，问「请写下您的标准做法，或发一份现成的说明（链接、文件名都可以）」。其中必有：「客户只说一句『想拍婚礼』，您先问他哪几件事？」「遇到没拍过的类型，您怎么说？」
  - 「您对 Agent 的看法」（3 题）：说话方式像不像您、哪里要改；判断和交给真人的时机对不对；还有什么必须知道、绝对不能说。
  - 「您的原话」（3 题）：您对客户说过一百遍的话；怎么称呼客户；怎么拒绝一个档期冲突的客户。
- 每个技能再加 1–2 题：一个真实案例（背景引用对话），和规则不适用的例外。

### 语义结构

- 页面分几个板块，用目录切换，每个板块旁边标题数：
  - Agent 介绍：它做什么、工作流程、怎么说话、怎么判断能不能说。
  - 知识缺口：需要专家补的事实。
  - 待回答问题：按组排列，每组一个说明问题性质的小标题，比如「口径不一致，需要您定一个说法」。
- 每道题一张卡片：
  - 稳定题号（C01、C02…，改文案不改题号）
  - 短标题
  - 背景：引用聊天或资料里的原话，用「」标出
  - 一句明确的问题
  - 回答区：选择题列出选项，加一个补充说明框；开放题只有一个文本框
- 「Agent 会这么说」这类原话，用小圆角标签显示。好的说法和不好的说法左右对照。

### 样式

- Hatch 的样式：米白底 #faf8f2，卡片 #fffdf8，细边线 #e2dccd；强调色只用蜂蜜黄 #f5b700，搭配浅黄底和深黄字；正文 16px，行高 1.75；大标题粗而紧凑；大圆角卡片，阴影很轻。
- 手机优先：单栏布局，目录吸顶、可以横向滑动；点击区域要大，输入框字号不小于 16px；保存和提交按钮固定在右下角，注意 safe-area。
- 克制：不用图标堆砌，不放营销式文案，没有多余的副标题和说明文字，让版式本身表达层次。
- 保存状态始终可见：「保存（3 题有修改）」「已保存」。保存失败时保留输入内容，并明确提示。
- 提交后整页变为只读，并显示「已提交」。

### 样式类

页面已经带了 Hatch 的基础样式和类名：`sidebar` `nav-link`(`active`) `badge` `workspace` `eyebrow` `paper` `q` `q-head` `q-id` `scenario` `prompt` `group-title` `options` `option` `say` `example`(内含 `good`) `flow` `note` `clear` `actions` `save` `submit` `status` `error` `done`，以及 h1–h4、textarea、input。只写用这些类的 HTML 骨架，默认不写 `<style>`；只有页面确实需要基础样式覆盖不到的东西时，才加页面自己的 CSS。

### 数据

- 页面里不写任何接口或凭证，只用注入的 `window.hatch`：读取 `hatch.schema`、`hatch.answers`、`hatch.status`；修改 `hatch.save(id, value)`、`hatch.clear(id)`；提交 `hatch.submit()`。
- 题号必须和发布时的 schema 一一对应。

### 发布与修改

- 发布的 `html` 必须是一个自包含的 HTML 文件：脚本内联在 `<script>` 里，不引用任何外部资源。
- 页面必须带脚本：保存、清除、提交都靠它。没有脚本的页面，按钮点了没有用，发布会被拒绝。以参考页的脚本为底，题目由脚本按 `hatch.schema` 渲染。
- 修改页面 = 用同一个 `form_id` 再调用一次 `publish_form`：链接不变，已有回答按题号保留。绝不重新编号；新增题用新题号，删题不复用旧题号。
- 发布后把链接发给专家，然后继续手头的工作。专家提交后，会像专家说话一样收到一条「我填好了《…》，你看一下。(form_id: …)」，这时调用 `read_form` 读取回答，接着往下做。
