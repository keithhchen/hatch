# Hatch Desktop 基础 Agent 能力 Spec

本版替代上一版，保留完整功能范围，并把“减法”落实到架构：**消息写入一次、后续追加、历史原样读取；不在读取时动态重建内容，不再建立多份历史及其同步机制。** 注释 1

## 1. 目标与边界

技术栈保持：

**Desktop + LocalRunner + 云端 Runtime + pi + Kimi**

提供：

- 图片附加、理解、预览及再次加载。
- PDF／Office 附加、读取、创建、编辑、渲染及视觉校验。
- macOS／Windows 本地工具执行。
- 对话独立草稿、可靠提交、持久历史、分页和重连。

复用成熟 skills、scripts 和工具链。不默认做附件云同步，不建立逐文件授权系统，不另造 Agent loop 或文档解析框架。

以下为目标规格，不代表已经全部实现或验收。

## 2. 核心数据模型：一份消息历史

只保留三个职责明确的数据对象：

| 对象内容与归属 |                               |
| ------- | ----------------------------- |
| 本地附件    | 文件副本、稳定 ID、路径及元数据             |
| 对话草稿    | 本地保存的未提交文字、附件引用、提交状态          |
| 已提交消息   | 云端保存的有序消息记录，包含正文、附件关联、工具调用及结果 |

### 写入原则

- 提交时确定消息 ID、顺序、正文及附件关联。
- 工具调用、工具结果和后续消息追加到同一条历史中，不重复挂载到多条消息。
- 模型实际使用的图片表示，在首次进入历史时确定并保留；不能续聊时重新读取可变文件、重新编码而改变旧输入。
- 已提交内容不根据当前配置、skill 版本或文件状态重新解释。
- 流式输出属于进行中的 UI 状态；完成后的消息以持久化记录为准。

### 读取原则

- UI 历史分页、工具详情和模型续聊，都基于同一份已提交记录。
- UI 可以省略二进制内容、按需读取详情，但不生成另一份历史。
- 同一已提交边界重复读取，消息 ID、顺序和内容一致。
- 不在加载时重新解析文档、运行 skill、补附件、生成摘要或修补旧正文。
- 模型压缩沿用 pi 的机制，不另建历史版本或一致性系统；压缩结果记录一次后使用。

**删除动态重建与多份数据同步逻辑，而不是增加更多“保持一致”的判断。**

稳定的历史输入有利于 KV／prompt cache；实际命中与成本收益还需结合 Kimi、system prompt、tools 等完整请求验证。

## 3. 本地附件管理

支持选择、拖拽和粘贴。
```
用户提供文件／粘贴内容
  → 原生层复制或写入 Hatch 专用附件目录
  → 返回附件 ID、副本路径及元数据
```

要求：

- 图片、PDF、Office、普通文件共用附件接入方式。
- 每个附件独立命名，避免同名覆盖。
- 元数据包含文件名、MIME、大小、SHA-256、所属主机。
- 后续引用保存的副本，不依赖用户原文件继续存在。
- 附件副本不原地覆盖；文档编辑另存到 workspace 或输出目录。
- 草稿或消息仍引用的附件不得自动删除。
- 附件目录与凭据、内部数据库及配置目录分离。

**本地副本仍通过 local filesystem path 引用，不默认上传 OSS。**

## 4. Runner 权限与跨平台执行

采用简单目录授权：

| 资源默认权限                |          |
| --------------------- | -------- |
| Hatch 专用附件目录          | 只读       |
| 任务临时／输出目录             | 可读写      |
| 随包 skills、scripts、工具链 | 读取／执行    |
| 用户 workspace          | 沿用已有授权策略 |
| 凭据、内部数据库              | 不开放      |

- workspace 外的文件由原生层接收并复制，Runner 读取副本。
- 不建立额外逐文件授权系统。
- 权限同时作用于文件工具、shell 和其 Python／Node／LibreOffice 子进程。
- 阻止路径穿越和符号链接绕过权限。
- macOS 使用本地 shell；Windows 使用平台适配执行器，不要求用户安装 WSL。
- 提供工作目录、环境、stdout／stderr、退出码、取消和超时处理。

## 5. 随包工具链与 Skills

随安装包提供：

- Python 及所需包。
- Node.js 及所需依赖。
- LibreOffice。
- Poppler，包括 `pdftoppm`、`pdfinfo`。
- 完整文档 skills 及必要 scripts。

要求：

- 不依赖用户安装开发环境或配置 PATH。
- scripts 使用可解析的随包路径。
- 依赖缺失、转换失败、文件不支持时明确报错。
- 不以假文件、静态预览或静默降级冒充成功。
- macOS、Windows 分别验证实际脚本执行。

## 6. 图片理解

### 用户附加图片
```
本地保存副本
  → 准备稳定的模型图片表示
  → 传输实际图片数据至 Runtime
  → pi 转换为 Kimi 多模态输入
```

- 模型收到图片数据，不是电脑路径。
- 可以为模型缩放／编码，但不覆盖本地原图。
- 图片进入模型历史后，其表示保持固定，续聊不重新生成。
- 不要求先建立永久 OSS 附件对象。

### Agent 主动看图
```
Agent 调用图片读取工具
  → LocalRunner 读取图片
  → 工具结果包含图片内容
  → pi 交给 Kimi
```

适用于本地图片、截图和文档渲染页面。

**生成 PNG 或返回路径，不等于模型已经看过；必须实际回传图片内容。**

## 7. PDF／Office 读写

覆盖 PDF、DOCX、XLSX、PPTX；旧格式 DOC、XLS、PPT、RTF 通过工具链处理并验证兼容性。

默认链路：
```
消息中的文件引用
  → 加载对应 skill
  → 本地工具读取／编辑／渲染
  → 工具结果追加到消息历史
```

要求：

- 不默认把整份 PDF／Office 作为原生多模态输入上传。
- 读取、创建和编辑经过对应 skill。
- 不在上传或加载历史时自动重新提取正文并塞进旧消息。
- 文字、结构由成熟工具提取；布局敏感任务渲染页面并实际看图。
- 输出真实可打开、符合任务要求的文档。
- 默认另存，不覆盖用户原文件或附件副本。
- 校验结构和视觉结果，不能只检查脚本退出码。
- 同一工具执行结果保存一次，续聊直接复用记录，不自动重跑。

## 8. 对话独立草稿

按 `account_id + conversation_id` 本地持久化：

- 未发送文字。
- 附件引用。
- 准备／提交状态。
- 逻辑消息 ID。

行为：

- A → B → A，恢复 A 的文字和附件。
- 不串草稿，不因切换直接清空附件。
- App 重启后恢复。
- 发送成功只清理本次提交内容，不覆盖后来输入的新内容。
- 失败时保留或恢复文字及附件。

不做跨设备草稿同步。同一对话多窗口同时编辑的行为需明确后实现，不引入协同编辑系统。

## 9. 提交与确认
```
附件准备完成
  → 提交正文、附件引用及必要图片内容
  → Runtime 持久化消息
  → 返回接受确认
  → Agent 执行
```

- 附件关联随消息写入，不在读取时补造。
- 同一逻辑消息 ID 重试，只接受一次，不重复启动任务。
- `socket.send()` 成功不等于服务端接受。
- 可以乐观清空编辑框，但必须保留恢复数据。

| 状态行为    |                |
| ------- | -------------- |
| 准备中／提交中 | 显示状态，保留恢复数据    |
| 已接受     | 清理对应待提交内容      |
| 明确失败    | 保留或恢复，允许重试     |
| 结果未知    | 先查询服务端，再决定是否重试 |

消息提交失败与已接受后的模型运行失败分别呈现。

## 10. 历史加载与附件预览

历史页返回已保存的正文、附件引用和必要元数据，不返回整份文件或重复的大工具结果。

- 附件卡片依据消息中的引用显示。
- 本地主机从副本加载预览，提供打开／另存为。
- 工具详情通过记录 ID 按需读取。
- 使用共享预览缓存、请求去重和资源释放。
- Blob URL、下载状态、预览错误等仅属于 UI，不写入旧消息。
- 文件缺失、所属主机不可用、加载失败明确显示，不改写历史内容。
- 模型上下文压缩不删除聊天消息及附件关联。

**动态的是展示状态，不是历史事实。**

## 11. 分页、重连与连接状态

- 最近一页优先，按完整轮次和稳定游标读取。
- 已固定的旧页不因新增消息漂移。
- 翻页保留滚动位置。
- 重连从已确认位置获取缺失记录，不重新构造整段历史。
- 消息按稳定 ID 接入，避免重复。
- 进行中的 UI 状态最终由持久化终态替换。
- 切换对话后丢弃旧请求的迟到响应。

分别显示：

**准备中／加载历史／连接中／在线／离线或失败。**

不能因为尚未加载完成就显示“离线”。

## 12. 旧数据与本轮边界

- 新附件默认本地副本、主机绑定引用。
- 旧 OSS 附件仅在明确的历史读取边界按原引用读取，不为新消息继续双写。
- 不静默替换存储来源，不破坏旧记录。
- 本轮不承诺附件跨设备同步。
- 传输、分页及缓存限制不等于删除历史。
- 不新建附件云平台、逐文件授权系统、多份历史投影库或额外版本框架。

## 13. 验收与发布

### 核心验收

- workspace 外文件附加后可由 Runner／skill 读取。
- 原文件移动或删除后，副本仍可用。
- 草稿切换、重启、提交期间继续输入均不丢失。
- 失败与结果未知可恢复，重试不重复提交或执行。
- 用户图片和工具返回图片均能被 Kimi 实际理解。
- PDF／Office 能真实读写、打开、渲染和看图校验。
- 重开历史后附件可加载；缺失时明确报错。
- Runner 不能访问凭据和内部数据库。

### 一致性与缓存验收

- 对同一已提交边界重复加载，消息内容和顺序一致。
- 重启、重连及配置变化不重新解释旧消息。
- 续聊不会自动重跑旧文档解析或重新编码旧图片。
- 相同历史对应相同模型输入前缀；实际缓存命中与费用单独测量。

### 发布

- 自动化测试、真实集成测试、OS UAT 分开报告。
- macOS、Windows 均在真实安装包上验收。
- 云端变更部署并验证；Desktop 走正常 CI/CD。
- 版本、源码、tag、安装包证据一致，两端安装包均可下载后才能宣称 release 完成。
- 不把 fixture、preview 或未签名产物说成已通过正式产品验收。

## 14. 待定参数

仅剩具体参数与交互选择：

- 文件大小、附件数量、缓存预算。
- 附件保留与安全回收规则。
- 同一对话多窗口编辑草稿的行为。

主架构不再摇摆：**本地附件副本＋目录授权＋独立草稿＋一份追加式消息历史；写入时确定，读取时不加工。**
