# 把经验变成结果

Hatch 帮你把自己知道的、做过的、愿意分享的东西，变成别人可以使用的帮助。

你不需要配置一个 Agent，也不需要理解模型或系统内部的工作方式。你只需要说明想帮助别人得到什么，交给 Hatch 重要材料，补充自己的判断，并在关键时刻做决定。

## Hatch 为什么这样设计

Hatch 的出发点不是“把功能做出来”，而是“让一个具体的人真正得到结果”。这带来几条简单的原则：

- **从人的目标出发**：用户不是想创建一个对象、运行一个流程或上传一个文件，而是想完成一件真实的事，拿到一个可以继续使用的结果。
- **把复杂性留在 Hatch**：系统可以很复杂，但用户面对的路径应该清楚。用户表达意图、提供重要背景、判断关键取舍；Hatch 负责把复杂工作组织起来。
- **尊重经验背后的判断**：材料不只是文字。方法为什么有效、什么时候不能照搬、哪些边界不能越过，同样重要。
- **让结果能够被使用**：结果不应该只是“生成出来了”，而应该能被理解、检查、修改、分享或交付。
- **减少用户承担的成本**：少一点猜测，少一点重复输入，少一点不必要的配置，把注意力留给真正重要的决定。

因此，Hatch 不是一个堆满选项的工具箱，而是一条从经验、材料和目标走向结果的路径。

## 先找到你的路径

- **Creator**：你有自己的方法、案例或经验，希望把它变成别人可以使用的 Product。
- **Coding Agent 用户**：你希望把自己的 Coding Agent 工作记录、电脑里的文件或你有权限访问的网页内容，作为材料带进 Product。
- **Buyer**：你已经找到一个 Product，希望用它处理自己的问题并获得结果。

## 核心概念

- **Product**：围绕一个清晰承诺，持续帮助别人完成一类事情的内容和方法。
- **Creator**：提供方法、经验和边界的人。
- **Buyer**：使用 Product 获得帮助的人。
- **About You**：Hatch 用来了解 Creator 的方法、判断和边界的对话。
- **Review**：Creator 和 Hatch 一起检查结果是否符合这套方法的环节。
- **Brief**：Buyer 开始一次具体事情前，需要提供的目标和背景。

## 一、如果你是 Creator

### 1. 先说清楚你想帮助别人得到什么

登录 Creator 账号，创建一个 Product，填写名称和承诺：

- **名称**：让别人一眼认出它能帮助自己做什么。
- **承诺**：用一句人话说明使用后能得到什么结果。

例如：

> 帮助创作者把零散经验整理成可以执行、可以复用的答案。

承诺不是技术说明，也不是功能清单。它应该描述一个人真正想取得的进步。

### 2. Files：交给 Hatch 你愿意使用的材料

你可以直接上传文章、笔记、案例、视频整理稿或方法说明。也可以从 Coding Agent 导入内容；两者是并列的材料来源，最后都会进入同一个 Product。

上传前只确认：这些材料属于你，或你有权使用；它们确实能帮助别人理解你的方法；你愿意让它们参与这个 Product。

![Creator 的 Files 页面](screenshots/creator-files-real-uat.png)

### 3. About You：告诉 Hatch 哪些内容最重要

Hatch 会根据材料了解你的方法。你可以用平时对同事或客户说话的方式回答：

- 你的方法真正解决什么问题。
- 哪些判断最重要。
- 哪些情况不能照搬。
- 什么样的答案才符合你的标准。

这一步不是让你把材料再抄一遍，而是把材料背后的经验、取舍和边界说清楚。

![Creator 的 About You 页面](screenshots/creator-about-you-real-uat.png)

### 4. Review：确认结果像不像你的方法

Review 会把 Product 放进一些具体场景，让你查看它会怎样回答。你要关注：

- 它有没有解决目标问题。
- 它有没有用对你的方法。
- 它有没有越过你的边界。
- 如果不满意，应该怎样改。

你可以接受结果，也可以指出问题后重新整理。重要修改会形成新的版本，之前的工作仍然保留。

### 5. Brief：让 Buyer 容易开始

Brief 是 Buyer 开始一次具体事情前要回答的问题，例如目标、现状、限制或截止时间。

真正影响结果的问题设为必填，不重要的问题设为可选。问题应该让 Buyer 容易回答，而不是要求 Buyer 理解你的内部流程。

### 6. 最后决定是否发布

当你准备好让别人使用这个 Product 时，由你决定发布。发布意味着：你愿意让 Buyer 按照这个承诺开始使用你的方法。

## 二、从 Coding Agent 导入内容

Coding Agent 导入和手动上传一样，都是 Product 的材料来源。它适合带入你已经看过并确认过的内容。

### 可以导入什么

1. **Coding Agent 本身的聊天工作记录**：例如 Codex、Claude、OpenClaw、WorkBuddy 等 Agent 中与你自己的工作、方法、案例和判断有关的对话。
2. **本地电脑上的文件**：例如笔记、文档、整理稿、案例或你已经批准的资料。
3. **浏览器中你有权限访问的网页**：例如你自己的社交媒体、内容后台、工作后台或其他登录后才能看到的页面。

Hatch 只使用你明确选择并有权使用的内容。你可以先预览，再决定是否带入哪个 Product。

### 普通用户的操作

1. 在 Coding Agent 中点击 **Connect Hatch** 或 **Authorize**。
2. 确认浏览器显示的是你自己的 Creator 账号和 Product 文件权限。
3. 点击同意，授权会自动完成并返回 Coding Agent。
4. 选择要带入的内容，先预览，再明确确认。
5. 选择目标 Product，点击上传。
6. 在 Product 的 Files 页面确认材料已经出现。

你不需要复制授权码、手动运行命令或接触 token。上传前只需要确认内容归属、预览结果和目标 Product。

![Coding Agent 授权页面](screenshots/context-intake-oauth-consent-20260819.png)

## 三、如果你是 Buyer

### 1. 先理解 Product 的承诺

从 Creator 分享的 Product 链接进入。开始前，你应该能看懂：

- 谁创建了这个 Product。
- 它承诺帮你完成什么。
- 你需要提供哪些背景。

如果一个 Product 的承诺与你的问题无关，就不要勉强开始；先找到更适合自己的帮助。

![Buyer 的 Product 详情页：先确认承诺、边界和访问方式](screenshots/buyer-product-detail-real.png)

确认适合之后，点击 **Get access**。如果这是一个需要加入账户的 Product，Hatch 会先让你确认当前的 Product 和 release：

- Product 名称和 Creator 是否正确。
- 你获得的是哪一个已批准版本。
- 访问是否为永久访问，以及是否需要付款。

![Buyer 的访问确认页：确认 Product 和 release](screenshots/buyer-checkout-confirm-real.png)

点击 **Add to my account** 后，访问会写入你的账户。成功页会给出下一步：打开 Desktop、查看订单收据，或查看访问详情。

![Buyer 的访问成功页：打开 Desktop 或查看访问详情](screenshots/buyer-order-success-real.png)

![Buyer 获得 Product 访问权限](screenshots/buyer-entitlement-success-20260819.png)

### 2. 回答开始问题

只回答和这次事情有关的内容。必填问题帮助 Product 理解你的目标，可选问题只在它确实能改善结果时填写。

### 3. 让 Product 帮你工作

提交背景后，Product 会按照 Creator 的方法处理你的问题。你要关注的是结果是否能解决当前事情，以及是否需要补充或调整自己的要求。

![Buyer 获得结果](screenshots/buyer-task-complete-20260819.png)

### 4. 把结果带回你的工作

好的结果不是只能留在 Hatch 里。你应该能够继续阅读、修改、分享、提交，或把它作为下一步工作的起点。

## 四、开始前的一分钟

### Creator

- 用一句话说清楚你要帮助别人取得的结果。
- 只提供你愿意交付、并有权使用的材料。
- 用自己的话说明方法、判断和边界。
- 在 Review 中检查结果是否真正像你的方法。
- 写出 Buyer 真正需要回答的问题。
- 由你决定何时让别人开始使用。

### Coding Agent 用户

- 只选择自己确认过的聊天记录、文件或网页内容。
- 先预览，再确认导入。
- 确认目标 Product。
- 导入后到 Product Files 页面查看结果。

### Buyer

- 先读懂 Product 的承诺。
- 只填写这次事情真正需要的信息。
- 判断结果是否真的能帮助你继续行动。

## 最后

Hatch 的价值，不是让你看到更多功能，而是让你更容易从自己的经验和目标出发，得到一个可信、可理解、可以继续使用的结果。

不要只问“这个功能做出来了吗”。更重要的问题是：

> 用户是否因此更容易成功？
