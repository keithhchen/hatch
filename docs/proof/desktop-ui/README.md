# Desktop UI visual evidence and UAT boundary

This document separates real product UAT from historical visual references for
the Tauri Hybrid shell. The old `DesktopPreview` fixture has been retired. The
static images generated by that fixture remain in this directory for design
history only; they are not product UAT evidence and must not be used to mark a
P4 requirement as passed.

For requirement-level status and evidence boundaries, see
[acceptance-matrix.md](acceptance-matrix.md). For reproducible package
candidates and protected target-device workflows, see
[automated-ci-uat.md](automated-ci-uat.md). For the signed/notarized release
gate, see [release-uat-contract.md](release-uat-contract.md).

## Real product evidence currently available

The current macOS product evidence comes from the built ad-hoc `.app`, not the
retired fixture:

- A cold launch on 2026-08-11 showed native traffic lights and title chrome,
  the ordinary Sign in surface, and no Login Keychain unlock prompt. The
  checked-in capture is `final-sign-in-1180x780.jpeg`.
- The same built app exposed the native View menu with dynamic sidebar,
  inspector, zoom, and fullscreen commands, and opened Settings as an
  independent `Hatch Settings` window.
- A real production UAT sign-in loaded two entitled Creator Agents (Maya and
  Seth), and switching the selected Agent updated the real entitlement-derived
  Agent projection. Both corresponding production `GET /v1/conversations`
  requests returned HTTP 404 `Route not found`; Send therefore remained
  correctly disabled. This is a production Runtime deployment blocker, not a
  passed Conversation/Composer UAT.
- The product build keeps WebKit devtools disabled. Product context-menu,
  valid-grant artifact opening, and cross-platform system integration remain
  acceptance items unless explicitly listed as real product UAT below; a
  fixture observation is never substituted for them.
- Strict local ad-hoc package construction is reproducible with:

  ```text
  cd desktop-app
  npm run build:app
  npm run build
  ```

  These commands produce UAT-only artifacts. They do not create a
  Developer-ID-signed, notarized release and do not prove clean-account
  Keychain restart behavior.

## Automated evidence

The repository currently records automated evidence independently of the old
images:

- Renderer: 24 files / 119 tests
- Rust Tauri library: 46 passed / 1 ignored (unlocked Keychain smoke)
- Runtime: 226 Node subtests with an isolated `HATCH_RUNTIME_DATA_DIR`
- LocalRunner: 43 tests, including filesystem, shell, and macOS Seatbelt suites
- `npm run build:web`, strict ad-hoc `.app`/DMG verification, and the release/UAT
  artifact helper tests

The ad-hoc DMG hash and byte count are recorded in
[`docs/proof/installable-desktop-v1.json`](../installable-desktop-v1.json).
The ad-hoc package is process-memory-only and must not be described as a
signed production distribution. The SemVer tag lane may promote the exact
candidate to the dedicated OSS UAT download prefix, but it never attaches the
package to a GitHub Release.

## Real product UAT procedure

When a product UAT is run, record the exact app/package identity, platform,
window size, application zoom, account state, workspace grant state, and a
fresh screenshot or accessibility observation. The minimum macOS sequence is:

1. Build or install the exact ad-hoc candidate and record its SHA-256.
2. Cold-launch it with no Login Keychain prompt; inspect the native title bar,
   traffic lights, application menu, and window lifecycle.
3. Exercise the product flow under the intended account and workspace grant;
   do not substitute fixture IDs or fixture notes for cloud Conversations.
4. Record failures separately for native menus, pane collapse/overflow,
   context menus, Quick Look/Open, drag/drop, accessibility, and recovery.
5. Attach the screenshot/logs to the exact package evidence and update the
   [acceptance matrix](acceptance-matrix.md) only for the behavior actually
   observed.

The protected signed-release sequence adds Developer ID identity checks,
notarization/stapling, clean-account Keychain restart, and post-UAT approval;
its contract is documented in
[release-uat-contract.md](release-uat-contract.md). The CI candidate and
target-device workflows are documented in
[automated-ci-uat.md](automated-ci-uat.md).

## Unaccepted P4 boundaries

The following remain external until real product evidence exists:

- one real Account with Creator Agent A's three Conversations and Creator Agent
  B's two Conversations, including cross-agent authorization rejection;
- three real product windows with independent cloud Conversation, Workspace
  grant, draft, zoom, pane, and scroll state, plus renderer reload/application
  crash observer recovery without replay;
- signed Developer ID/notarized macOS release, clean-account Keychain
  read/write after restart, and the post-UAT reviewer record;
- Windows installer and real Windows frame/menu behavior, Explorer/Open,
  Narrator, Snap, high-DPI/multi-monitor, IME, fullscreen, and drag/drop;
- VoiceOver, real Finder/Explorer drag/drop, valid-grant Quick Look/Open, and
  product context-menu checks that exclude `Inspect Element`;
- Light/Dark, Increase Contrast, Reduced Motion, system accent, and live-resize
  behavior on each target OS.

These boundaries are intentional. The implementation and automated tests may
prove contracts at code level, but only a real product run on the target
platform can close the corresponding P4 row.

## Native UX judgment

The intended desktop model remains: native window/menu/system integration at
the shell boundary, with React/WebView owning transcript, Markdown, code,
tables, tool activity, and Composer content. The historical images can inform
visual review, but the acceptance decision must come from the current product
build and the requirement-level matrix above.
